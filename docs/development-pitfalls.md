# Development Pitfalls & Project Conventions

> Lessons learned from real debugging sessions in this repository. Read before writing tests
> or touching infrastructure code. Each item cost at least one wasted TDD cycle to discover.

## 1. Build & Test Hygiene

### 1.1 Incremental compilation is unreliable here
- `mvn test` repeatedly served stale `.class` files and stale surefire reports: tests failed
  (or passed) for reasons unrelated to the current source.
- **Rule**: after editing `src/main`, run `mvn clean test` (or `mvn clean test -Dtest=X`),
  not plain `mvn test`.
- **Rule**: never suppress Maven output (`| Out-Null`) while iterating. Two "test failures"
  were actually compile errors hidden behind suppressed output.

### 1.2 Detecting a stale surefire report
- Identical `Time elapsed` values across runs on changed code = stale report; the run never executed.
- When a result contradicts the code just written, suspect staleness FIRST (check report
  timestamps, then `mvn clean`), logic second.

### 1.3 Feedback-loop cost hierarchy
- Full Spring context boot is ~15-25s per class; plain unit tests are milliseconds.
- **Rule**: pure-logic components (validators, limiters, guards, mappers) get a plain JUnit test
  FIRST; wire them into controllers/jobs only after green. Integration tests verify wiring and
  HTTP contracts, not algorithms.
- Concrete case: `LoginRateLimiter` bugs (double-counted failure, sentinel wipe) were found in
  seconds by a unit test after three expensive integration cycles missed them.

## 2. Test Design Rules

### 2.1 State preconditions explicitly before writing a RED test
- A rate-limit test used a nonexistent username, so its final assertion could not distinguish
  "lockout works" from "user does not exist".
- **Rule**: list every precondition (seeded rows, existing accounts, config overrides) and
  confirm they exist in the fixture before writing the test.

### 2.2 Use seeded accounts and fixtures
- Seeded logins (from `UserRegistry.seedAccounts`): `admin/admin`, `warehouse/warehouse`,
  `customer/customer`.
- SQL fixtures follow the `DELETE FROM ...; INSERT ...` pattern in `src/test/resources/*-test-data.sql`;
  create a new fixture per feature instead of mutating shared ones.
- Auth helper: `TestAuthHelper.obtainAccessToken(mockMvc, objectMapper, username, password)`.

### 2.3 Derive expected values from domain rules, don't guess
- An order-audit test guessed 2 revisions where create+pay+ship produces 3 (one revision per
  state transition). Count transitions before asserting counts.

## 3. Codebase Conventions

### 3.1 Identifiers are server-generated UUIDs
- Product/order ids are generated by handlers; clients can NEVER choose them. Tests must capture
  the id from the create response.
- APIs expose external ids (`external_id` columns); internal `Long id`s are JPA/Envers keys.
  Audit endpoints accept external ids and resolve internally.

### 3.2 Exception -> HTTP status mapping (ApiExceptionHandler)

| Exception | Status |
|---|---|
| MethodArgumentNotValidException | 400 |
| IllegalArgumentException | 400 |
| IllegalStateException (domain transition violation) | 409 |
| ResourceNotFoundException | 404 |
| AccessDeniedException (@PreAuthorize denial) | 403 |
| AuthenticationException | 401 |
| anything else | 500 |

- Gotcha: the blanket `ExceptionHandler(Exception.class)` swallows Spring Security exceptions
  unless dedicated handlers exist. Adding new security mechanisms requires rechecking this table.
- Handlers must throw `ResourceNotFoundException` (not IllegalArgumentException) for missing
  entities so clients get 404, not 400.

### 3.3 H2 seeded timestamps skew by the JVM timezone offset
- Fixtures using `DATEADD('MINUTE', -5, CURRENT_TIMESTAMP)` read back shifted (~+3h here), so
  "5 minutes ago" appears to be in the future.
- **Rule**: for fixtures that must be expired/past, seed >= 4 hours back
  (`DATEADD('MINUTE', -240, CURRENT_TIMESTAMP)`), or create data through the public API and
  trigger time-dependent behavior by invoking the job bean directly.

### 3.4 Envers audit queries return Object[] tuples
- `forRevisionsOfEntity(entity, false, true)` yields `Object[] {entity, AuditRevisionEntity,
  RevisionType}` — NOT `List<Object>`. Wrong cast throws ClassCastException at request time,
  surfacing as an opaque 500.

### 3.5 Architecture rules affecting placement
- Hexagonal: application handlers depend on ports (`application/ports` interfaces), never on
  infrastructure services; adapters implement ports
  (see `PaymentFailureNotifier` -> `WebSocketPaymentFailureNotifier`).
- WebSocket channels: broadcast `/topic/orders/{id}`; per-user `/user/queue/orders`
  (username == customerId for non-admin flows).
- Domain state machine lives in `OrderStatus.canTransitionTo`; violations throw
  IllegalStateException (mapped to 409).

## 4. Process Rules That Saved Time

1. Confirm scope + behavior list with stakeholders BEFORE the first RED test (TDD planning step).
   Every gap session started well because of this; skipping it caused the precondition mistakes.
2. Vertical slices: one RED test -> minimal GREEN -> next. Never batch multiple tests before
   implementing (horizontal slicing produced broken assertions twice).
3. When a GREEN implementation is written but the test still fails identically, suspect a stale
   build before rewriting correct code (cost two unnecessary rewrites once).
4. Keep a running list of discovered conventions in this file — each entry above was rediscovered
   at least once before being written down.
